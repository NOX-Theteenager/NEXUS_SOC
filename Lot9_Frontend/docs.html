Section 1

Prise en main

Cette documentation est embarquée dans la plateforme : elle reste consultable quand le réseau est coupé, et elle est versionnée avec le code. Le CENADI exploite NEXUS SOC sans document externe.

Le chemin le plus court vers une instance fonctionnelle, avec données de démonstration. Seule PostgreSQL est réellement obligatoire : Kafka et Wazuh peuvent être ajoutés plus tard, le service de scoring est conçu pour se dégrader proprement sans eux.

  1. PostgreSQL dans Docker (image TimescaleDB officielle).
  2. Schémas et jeu de démonstration appliqués dans l'ordre.
  3. Environnement Python dédié et dépendances installées.
  4. Serveur uvicorn qui monte les routeurs et sert le frontend sur /app/.
  5. Tests pytest pour valider le parcours de bout en bout.

Section 2

Architecture du socle

Sept composants travaillent ensemble : un agent endpoint léger en Go, une passerelle d'ingestion FastAPI, un pipeline temps réel via Kafka, deux modèles d'IA, un moteur SOAR avec garde-fous, un module de restitution bilingue, et la console opérateur.

# Chaîne de traitement, de la collecte à la restitution Agent Go (~5 Mo, egress-only, HMAC-SHA256) → POST /ingest (FastAPI) → Kafka KRaft (nexus.telemetry) → Normalisation + corrélation MITRE ATT&CK (8 règles) → Modèles IA : M1 Isolation Forest réseau · M2 UEBA fraude interne → nexus.alerts → SOAR (4 playbooks, validation humaine sur impact fort) → Portail + notifications + rapport HTML

Le stockage repose sur deux briques : TimescaleDB (PostgreSQL 16 avec extension séries temporelles) pour le relationnel, les alertes et l'audit ; Wazuh Indexer (OpenSearch) pour le stockage chaud SIEM.

Cloisonnement des périmètres

Une seule instance héberge tous les périmètres supervisés. L'isolation est assurée par Row-Level Security PostgreSQL : chaque requête positionne app.current_tenant avant d'interroger les tables.

Deux rôles de base distincts : nexus_app (soumis à la RLS, vue d'un seul périmètre) et nexus_analyst (BYPASSRLS, vue cross-périmètre pour l'équipe SOC). Masquer un bouton dans l'interface est du confort ; l'isolation réelle est appliquée en base.

Section 3

Enrôler un agent

L'agent est un binaire Go d'environ 5 Mo, écrit en pur stdlib. Il est egress-only en HTTPS : aucun port entrant, il fonctionne derrière n'importe quel pare-feu. Chaque lot est signé en HMAC-SHA256 et conservé localement si le serveur est injoignable.

L'enrôlement se pilote depuis la console : SOC Analyst → Enrôlement d'agent. Trois étapes — choisir le périmètre, générer le jeton, choisir la voie de déploiement selon le contexte réseau du poste cible.

VoieQuand l'utiliserEndpoint
Commande shellLe poste atteint le serveur sur le réseau interneGET /provision/oneliner
QR codePoste isolé du réseau d'administration, terminal mobileGET /provision/qr/{id}
Archive .zipSegment coupé d'Internet, transfert par clé USBGET /provision/offline-pack/{id}
Import CSVEnrôlement d'un parc entier en une opérationPOST /provision/bulk

Commande à exécuter sur le poste

# Linux curl -fsSL "https://soc.cenadi.cm/provision/oneliner?token=nexus_xxx&hostname=POSTE-RH-12" | sudo sh # Windows (PowerShell en administrateur) Set-ExecutionPolicy Bypass -Scope Process -Force irm "https://soc.cenadi.cm/provision/oneliner?token=nexus_xxx&hostname=POSTE-RH-12&os=windows" | iex

Import CSV en masse

Le fichier attend un en-tête et les colonnes hostname,os,description. La console valide chaque ligne côté client avant tout envoi : doublons, OS inconnu et hôte vide sont signalés, et aucune ligne n'est transmise tant que le parc n'est pas confirmé. Après envoi, les jetons sont exportables en CSV — ils ne seront jamais réaffichés.

hostname,os,description POSTE-RH-12,windows,Bureau ressources humaines POSTE-RH-13,windows,Bureau ressources humaines SRV-PAIE-04,linux,Serveur de traitement de la solde

Configuration déposée sur le poste

{ "server_url": "https://soc.cenadi.cm/ingest", "enroll_token": "nexus_xxx", "hmac_key": "…", "agent_id": "…", "tenant_id": "<UUID du périmètre>", "interval_sec": 30, "watch_dirs": ["/home", "/tmp", "/var/log"], "queue_dir": "./queue", "queue_max_mb": 50 }

Déploiement de masse par Ansible

ansible-playbook -i inventaire.ini \ Lot7_Console_Fournisseur/install_templates/ansible_nexus_agent.yml \ -e "nexus_server=https://soc.cenadi.cm" \ -e "nexus_token=nexus_xxx" \ -e "nexus_tenant_id=<UUID>"
Cycle de vie des secrets

Le jeton d'enrôlement et la clé HMAC ne sont affichés qu'une seule fois. En cas de perte, utilisez la rotation de clé (POST /provision/rotate-hmac/{id}) : elle invalide immédiatement la clé courante, l'agent cessera d'émettre tant qu'il n'aura pas été reconfiguré. Prévoyez un accès au poste avant de lancer une rotation.

Section 4

Traiter une alerte

La file d'alertes est le poste de travail quotidien de l'analyste. Elle est ouverte sur SOC Analyst → Alertes : la file à gauche, le détail à droite — vous ne perdez jamais votre file en ouvrant une alerte.

Ce que porte une alerte

ChampCe qu'il dit
risqueScore 0–100 attribué par le modèle. Seuil d'alerte par défaut : 70.
raisonsListe des motifs renvoyés par le modèle — c'est l'explicabilité, affichée telle quelle.
mitreTechniques ATT&CK corrélées, ordonnées par phase dans le détail.
source_modeleModèle 1 (réseau) ou Modèle 2 (UEBA fraude interne).
entiteHôte ou compte concerné.

Échelle de risque

ScoreLectureDélai attendu
≥ 80CritiqueAction immédiate
60 – 79ÉlevéÀ traiter dans la journée
40 – 59MoyenÀ qualifier
< 40FaibleSurveillance

Règles de corrélation

Le moteur corrèle les événements sur une fenêtre glissante de 30 minutes (CORR_WINDOW_MIN) et couvre huit techniques :

TechniqueCe qu'elle détecte
T1059Exécution de commandes ou de scripts, processus lancé depuis /tmp
T1071Connexion vers un port de commande connu (4444, 6667, 1337…)
T1005Accès à des fichiers sensibles (shadow, passwd, dossiers de solde)
T1204Fichier exécutable ouvert depuis le répertoire de téléchargement
T1486Plus de 20 fichiers modifiés en moins de 5 minutes — rançongiciel
T1027Obfuscation : base64 inline, double extension, appel iex()
T1136Création de comptes, notamment en masse (plus de 5 en 10 minutes)
T1083Énumération de répertoires système et de la base de registre

Un incident est levé si au moins 3 tactiques distinctes sont observées dans la fenêtre, ou sur les combinaisons Execution + C2, Impact seul, ou Defense Evasion + Persistence.

Clore une alerte

  • Approuver l'action SOAR proposée si l'incident est confirmé.
  • Refuser en motivant : le motif est journalisé dans soar_audit.
  • Marquer faux positif : l'alerte sort de la file et alimente le taux de faux positifs utilisé par le suivi de dérive des modèles (section 6).

Produire une chaîne d'attaque de démonstration

Le collecteur sait émettre une séquence d'événements bruts reproduisant un scénario d'exfiltration complet. Ce n'est pas une alerte fabriquée en base : les événements passent par /ingest, signés, et c'est le moteur de corrélation qui reconstitue la chaîne.

sudo -E python3 /opt/nexus-agent/nexus_collector.py --simulate chaine

L'incident apparaît dans la file d'alertes avec son déroulé horodaté, la preuve de chaque étape et la décomposition de son score. Les deux autres simulations (--simulate exfil, --simulate portscan) alimentent les modèles d'anomalie et ne produisent donc pas de chaîne.

Raccourcis clavier

Dans la console : d tableau de bord, a alertes, v approbation SOAR, p périmètres, g agents, s santé, m supervision, e enrôlement.

Section 5

Playbooks SOAR et garde-fous

Quatre playbooks couvrent les types d'incident produits par le pipeline. Chaque action porte un niveau d'impact, et l'impact fort est le seul à ouvrir une demande de validation humaine.

Type d'incidentEnchaînement
Fraude internejournal d'investigation → notification → gel de compte → conservation des journaux
Exfiltrationjournal d'investigation → gel de compte → blocage IP → notification
Rançongicielcapture mémoire → isolation d'hôte → blocage IP → notification
Anomalie réseau / C2journal d'investigation → blocage IP → notification

Niveaux d'impact et réversibilité

ImpactActionsValidationRéversible
info / faiblejournal d'investigation, conservation des journaux, notificationsautomatiquesans objet
moyencapture mémoire, blocage IP, réinitialisation de mot de passeautomatique si risque ≥ 70blocage IP oui
fortgel de compte, isolation d'hôtehumaine, toujoursoui, depuis le journal

L'interface annonce l'impact et la réversibilité avant la confirmation : une isolation d'hôte se défait, une réinitialisation de mot de passe non.

Modes d'automatisation

  • Observe (dry_run=True) : toutes les actions sont proposées, aucune n'est exécutée.
  • Semi-auto (défaut en exploitation) : impacts faible et moyen automatiques si risque ≥ 70, impact fort en attente de validation.
  • Auto complet : toutes les actions s'exécutent. Non recommandé.

Journal d'audit

Toute action proposée, exécutée, refusée ou annulée est écrite dans soar_audit et consultable dans la console (Supervision ou Approbation SOAR), filtrable par périmètre, acteur et impact. Le journal répond à la question « qui a gelé ce compte, quand, sur quelle décision ».

À raccorder avant exploitation réelle

Les connecteurs SOAR — gel de compte AD/LDAP, isolation d'hôte, blocage IP périmétrique — sont simulés dans le démonstrateur. Ils doivent être raccordés aux annuaires et pare-feu réels du CENADI avant toute mise en exploitation.

Section 6

Supervision et dérive des modèles

La section Supervision de la console réunit trois lectures : les séries mesurées du socle, l'état de dérive des modèles, et le journal d'audit SOAR.

Séries temporelles

Les graphiques sont tracés en SVG, sans bibliothèque, depuis l'hypertable metrics agrégée par minute. Métriques suivies : cpu, score_risque, octets_sortants. Fenêtres : 1 h, 6 h, 24 h, 7 j.

Une absence de mesure ne se dessine pas comme une mesure

L'abscisse est proportionnelle au temps, pas au rang du point. Quand la collecte s'interrompt, la courbe se rompt, la zone est grisée sur toute la durée réelle de la coupure, et leur nombre est annoncé sous le graphique. Une plage vide signifie « rien n'a été mesuré ici » — jamais « la valeur est restée stable ».

Même règle sur le score de sécurité du portail : un jour sans télémétrie n'a pas de score, il interrompt la courbe. Un jour sans alerte n'est un 100 que si la plateforme collectait effectivement ce jour-là.

GET /admin/metrics?hours=24

Dérive des modèles

Un modèle entraîné sur des données passées se dégrade quand la réalité change. Le suivi mesure cet écart sur deux fenêtres consécutives de même durée.

IndicateurCe qu'il mesureSeuils
PSIÉcart entre la distribution de référence et la distribution courante > 0,10 surveillance · > 0,25 ré-entraînement
Glissement σDéplacement de la moyenne des scores, en écarts-type> 2σ alarme
Taux de faux positifsPart des alertes marquées faux positif par les analystes> 10 % alarme
Taux d'alertesAlertes rapportées au volume d'événementstrop bas : modèle permissif
GET /monitor/drift?days=7 # fenêtre réglable : 7, 14 ou 30 jours
Absence n'est pas santé

Si le module de monitoring n'est pas disponible sur le déploiement, la console affiche explicitement « calcul indisponible ». Ne lisez jamais cette absence comme « modèles sains » : la dérive n'est simplement pas mesurée.

Lire « non mesurable » et « indicatif »

Le PSI a besoin des deux fenêtres. Un modèle qui n'a produit aucune alerte sur l'une des deux périodes est donc non mesurable — ce n'est pas une panne, et ce n'est pas un verdict de bonne santé. La console affiche alors le nombre d'alertes de chaque côté pour que le manque se voie. Un historique irrégulier peut être non mesurable à 7 jours et parfaitement mesurable à 14 : c'est à cela que sert le sélecteur de fenêtre du panneau.

À l'inverse, un PSI calculé sur une poignée d'alertes est arithmétiquement juste et statistiquement muet : le découpage en déciles perd son sens. En dessous de 30 observations du côté le moins fourni, la valeur reste affichée mais l'étiquette passe à indicatif. Elle ne justifie pas à elle seule un ré-entraînement.

Rapport d'incident — langue et intégrité

Le rapport suit la langue du portail. La version française est celle figée en base au moment de l'incident et fait foi ; la version anglaise est rendue à la demande depuis les mêmes données, jamais traduite depuis le HTML.

Chaque rapport porte une empreinte SHA-256 en pied de page. Elle ne peut pas porter sur le document qui la contient : elle est calculée sur le document privé de son bloc d'intégrité, dont chaque ligne porte le marqueur NEXUS-INTEGRITY. N'importe quel destinataire la reproduit hors ligne, avec des outils standards :

grep -v NEXUS-INTEGRITY rapport-nexussoc-a7f3c91d.html | sha256sum

S'y ajoute un scellé HMAC-SHA256 sur les mêmes octets. Il est vérifiable par le SOC qui détient le secret de plateforme — pas par un tiers. Une signature Ed25519 serait publiquement vérifiable, mais aucune clé asymétrique n'existe dans le déploiement : l'annoncer reviendrait à promettre une garantie que la plateforme n'apporte pas.

Santé du socle

La section Santé système interroge /health/detailed toutes les 30 secondes et rend l'état service par service : scoring, Kafka, TimescaleDB, indexeur Wazuh. Un service dégradé ne signifie pas un socle arrêté — la page dit lequel, et ce qui reste opérationnel.

Section 7

Sauvegarde et restauration

Deux scripts du Lot 0 encadrent le cycle : backup.sh et restore.sh. Le déploiement souverain installe automatiquement une tâche cron quotidienne à 02 h 00.

# Sauvegarde manuelle BACKUP_DEST=/opt/nexus-backups KEEP_DAYS=14 ./Lot0_Socle/backup.sh # Restauration depuis une archive datée ./Lot0_Socle/restore.sh /opt/nexus-backups/nexus-2026-08-11.tar.gz # Vérifier la tâche planifiée crontab -l | grep nexus

Ce qui doit être sauvegardé

ÉlémentPourquoiReconstructible ?
Base TimescaleDBPérimètres, comptes, alertes, journal d'auditNon
Modèles .joblibM1 réseau et M2 UEBA entraînésOui, par ré-entraînement
Fichier .envSecrets JWT, pseudonymisation, baseNon — leur perte invalide tous les jetons
Index WazuhStockage chaud SIEMPartiellement, via réindexation
Une sauvegarde non testée n'est pas une sauvegarde

Exécutez une restauration sur une instance de test au moins une fois par trimestre. Vérifiez ensuite qu'une connexion aboutit et que la file d'alertes se charge.

Section 8

Déploiement hors ligne et souverain

Le déploiement cible est souverain et potentiellement coupé d'Internet. Aucune ressource ne doit être chargée depuis un réseau externe à l'exécution.

Ce que cela impose au frontend

  • Les trois familles de polices sont auto-hébergées sous Lot9_Frontend/fonts/ en WOFF2 et déclarées en @font-face. Aucun appel à un service de polices distant.
  • Les icônes sont des SVG en ligne. Aucune bibliothèque d'icônes distante.
  • Les graphiques sont produits en SVG par la page elle-même. Aucune bibliothèque de tracé.
  • La recherche de cette documentation indexe le DOM au chargement. Aucun moteur distant.

Pour régénérer les polices depuis un poste connecté : python3 Lot9_Frontend/fonts/fetch_fonts.py.

Application installable et mode hors ligne

Le frontend est une application web installable. Le service worker met les pages en cache, sert offline.html quand la navigation échoue, et reçoit les notifications d'alerte critique.

  • Chrome / Edge : icône d'installation dans la barre d'adresse.
  • Android : « Ajouter à l'écran d'accueil ».
  • iOS : « Sur l'écran d'accueil » depuis Safari.
Ajouter une page

Toute nouvelle page doit être ajoutée à PRECACHE_URLS dans sw.js, et CACHE_NAME incrémenté — sinon les anciens navigateurs continuent de servir la version précédente.

Déploiement souverain par OpenTofu

Mode recommandé en exploitation : la pile est déployée sur un serveur fourni par l'institution, aucune donnée ne quitte le site.

cd deploy/opentofu/ cp terraform.tfvars.example terraform.tfvars nano terraform.tfvars # server_host, institution_name, nexus_domain tofu init && tofu plan && tofu apply tofu output -raw postgres_password

La séquence exécute sept étapes en SSH : prérequis Docker, envoi des configurations et des sources, certificats Wazuh, démarrage de la pile, vérification de santé. Les secrets (PostgreSQL, JWT, administrateur Wazuh) sont générés automatiquement.

Sécurité

  • JWT HS256 maison : jeton d'accès 15 minutes, renouvellement 7 jours, rafraîchissement automatique sur 401 côté client.
  • HMAC-SHA256 sur chaque lot ingéré, jeton Bearer vérifié contre son empreinte en base — le secret en clair n'est jamais stocké.
  • Limitation de débit : 100 req/min global, 30 req/min sur /ingest.
  • Pseudonymisation stable des données personnelles par HMAC ; la correspondance inverse est réservée à l'administrateur pour enquête.
  • CORS restreint par NEXUS_CORS_ORIGINS ; jamais de joker avec identifiants.
  • Rotation et révocation par agent ou par périmètre entier en cas d'urgence.

Questions fréquentes

Le serveur a moins de 8 Go de RAM, est-ce jouable ?

Oui. Désactivez le service wazuh.dashboard et baissez OPENSEARCH_JAVA_OPTS. Vous conservez l'API et les interfaces, vous perdez l'exploration SIEM graphique.

Que se passe-t-il si le serveur tombe quelques heures ?

Les agents continuent de collecter. Les lots sont mis en file locale persistante, bornée par queue_max_mb, et rejoués à la reprise. Aucune perte tant que la file n'est pas saturée.

Peut-on remplacer un modèle par le sien ?

Oui, tout modèle scikit-learn enregistré en .joblib avec la structure attendue (model, scaler, features, threshold, risk_cfg) est accepté.

Comment mettre un nouveau système sous supervision ?

Par le formulaire interne : demande à l'équipe SOC. La demande est référencée, qualifiée, puis le périmètre est créé et les agents enrôlés.
