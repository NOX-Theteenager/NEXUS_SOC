Documentation NEXUS SOC

Guide complet de la plateforme SOC open source et souveraine : démarrage en 15 minutes, déploiement des agents sur tout type de parc, et choix entre cinq modes de déploiement du serveur (Docker, VM, cloud privé, souverain, auto-hébergé).

Démarrage rapide

Le chemin le plus court pour disposer d'une instance fonctionnelle en local, avec données de démonstration et tests automatisés validés (18/18 PASS).

  1. PostgreSQL dans Docker (TimescaleDB officiel). C'est la seule infrastructure obligatoire.
  2. Schémas + seed SQL appliqués dans l'ordre. Le seed crée 3 comptes de démonstration et des alertes prêtes à explorer.
  3. Environnement Python dédié (venv) et installation des dépendances.
  4. Serveur uvicorn qui monte tous les routeurs et sert le frontend PWA sur /app/.
  5. Tests pytest qui valident le parcours bout en bout.
# 1. PostgreSQL (TimescaleDB) en conteneur docker run -d --name nexus-pg-test \ -e POSTGRES_USER=nexus -e POSTGRES_PASSWORD=change_me -e POSTGRES_DB=nexus_soc \ -p 5432:5432 timescale/timescaledb:2.15.3-pg16 until docker exec nexus-pg-test pg_isready -U nexus -d nexus_soc; do sleep 2; done # 2. Schémas + seed (dans l'ordre) for f in Lot0_Socle/01_schema_patched.sql \ Lot7_Console_Fournisseur/01_schema_analyst.sql \ Lot7_Console_Fournisseur/01_schema_provisioning.sql \ Lot0_Socle/03_schema_notifications.sql \ Lot0_Socle/02_seed_demo.sql; do docker exec -i nexus-pg-test psql -U nexus -d nexus_soc -v ON_ERROR_STOP=1 < "$f" done # 3. venv + dépendances python3 -m venv .venv .venv/bin/pip install fastapi "uvicorn[standard]" psycopg2-binary numpy joblib \ email-validator python-multipart pytest httpx # 4. Serveur export DB_DSN="postgresql://nexus:change_me@localhost:5432/nexus_soc" .venv/bin/uvicorn run:app --port 8000 # 5. Tests (18 passed attendus) NEXUS_BASE_URL=http://127.0.0.1:8000 NEXUS_TEST_PWD=admin \ .venv/bin/pytest Lot6_Tests/test_api.py -v
Astuce

Kafka et Wazuh ne sont pas requis pour démarrer : le service de scoring est conçu pour fonctionner en dégradation gracieuse. Vous pouvez les ajouter plus tard via le docker-compose.yml du Lot 0.

Architecture

Sept composants principaux travaillent ensemble : un agent endpoint léger en Go, une passerelle d'ingestion FastAPI, un pipeline temps réel via Kafka, deux modèles d'IA (Isolation Forest réseau + UEBA fraude), un moteur SOAR avec garde-fous, un LLM Analyst pour la restitution bilingue, et une console opérateur multi-tenant.

Le stockage repose sur deux briques : TimescaleDB (PostgreSQL 16 + extension séries temporelles) pour le relationnel et l'audit, et Wazuh Indexer (OpenSearch) pour le stockage chaud SIEM. L'isolation entre clients est assurée par Row-Level Security PostgreSQL, avec un rôle nexus_app filtré et un rôle nexus_analyst BYPASSRLS pour la supervision cross-tenant.

Le diagramme d'architecture complet est disponible dans 00_Documents/Architecture_NEXUS_SOC.drawio.

Installation des agents endpoint

L'agent est un binaire Go d'environ 5 Mo, écrit en pur stdlib (aucune dépendance externe), egress-only HTTPS, avec signature HMAC-SHA256 des lots et store-and-forward local. Il fonctionne derrière n'importe quel pare-feu.

a Compiler l'agent

# Linux amd64 (~5,0 Mo) CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -ldflags="-s -w" -o nexusagent . # Windows amd64 (~5,3 Mo) CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build -ldflags="-s -w" -o nexusagent.exe .

b Configurer (config.json sur le poste)

{ "server_url": "https://soc.votre-domaine.cm/ingest", "enroll_token": "nexus_xxx", "hmac_key": "…", "agent_id": "agent-poste-001", "tenant_id": "<UUID>", "interval_sec": 30, "watch_dirs": ["/home", "/tmp", "/var/log"], "queue_dir": "./queue", "queue_max_mb": 50 }

2 CSV bulk

Format attendu : une ligne par poste, colonnes hostname,os,description. Envoyez le contenu à POST /provision/bulk, recevez un CSV de tokens à distribuer.

3 Pack offline

Téléchargez GET /provision/offline-pack/{agent_id} qui contient le binaire (Linux et Windows), un config.json pré-rempli, et les scripts install_linux.sh / install_windows.ps1. Copiez-le sur clé USB, transférez sur le poste, lancez l'installeur.

L'endpoint GET /provision/qr/{agent_id} renvoie un PNG en base64. Scanné, il donne la commande curl | bash complète sur le terminal du poste.

1 Docker Compose (par défaut)

Le mode le plus simple. Le docker-compose.yml du Lot 0 démarre l'intégralité de la pile : Kafka KRaft, TimescaleDB, Wazuh Indexer + Manager + Dashboard, scoring service. Toutes les healthchecks sont configurées, le démarrage est attendu via --wait.

sudo sysctl -w vm.max_map_count=262144 cd Lot0_Socle && unzip nexus-soc-socle.zip && cd nexus-soc-socle cp .env.example .env # adapter les mots de passe docker compose up -d --wait docker compose ps curl http://localhost:8000/health
RAM

La pile complète demande 8 Go minimum (Wazuh Indexer est l'élément le plus gourmand). Sur 4 Go, commentez le service wazuh.dashboard et utilisez seulement l'API.

2 Machine virtuelle (Ubuntu / Debian)

Pour une organisation préférant une VM dédiée plutôt que des conteneurs. Recommandé : Ubuntu 22.04 LTS, 8 Go RAM, 50 Go disque. La séquence est identique à Docker Compose, plus la configuration d'un service systemd pour redémarrer automatiquement la pile.

  • Installez Docker selon la procédure officielle.
  • Clonez le dépôt dans /opt/nexus-soc.
  • Créez une unité /etc/systemd/system/nexus-soc.service qui lance docker compose up au boot.
  • Configurez un reverse proxy (Nginx / Caddy) en frontal pour HTTPS et le routage /app vers le frontend.

3 Cloud privé (AWS/Azure/GCP en VPC dédié)

Pour un déploiement à plus grande échelle, restant sous votre contrôle, dans un VPC isolé. Architecture cible :

  • Calcul : Kubernetes managé (EKS, AKS, GKE) avec auto-scaling.
  • Base : PostgreSQL managé (RDS, Cloud SQL) avec extension timescaledb ou installation manuelle.
  • Pipeline : Kafka managé (MSK, Confluent Cloud, Event Hub) ou auto-géré sur Kubernetes.
  • Stockage objet : S3/Blob pour les sauvegardes et les modèles IA.
  • Réseau : VPC privé, endpoints VPC, pas d'IP publique pour la base.
Conformité

Pour un usage au Cameroun, privilégiez les régions les plus proches géographiquement (AWS Cape Town, Azure Johannesburg) en attendant une présence souveraine. Les administrations publiques doivent rester sur le mode souverain ci-dessous.

4 Déploiement souverain (OpenTofu)

C'est le mode recommandé pour les administrations publiques camerounaises. La pile est déployée par un module OpenTofu (deploy/opentofu/) directement sur un serveur fourni par l'institution. Aucune donnée ne quitte le site.

  1. L'institution provisionne un serveur physique ou une VM (Ubuntu 22.04, 8 Go RAM minimum) avec accès SSH.
  2. Vous renseignez terraform.tfvars : IP serveur, clé SSH, nom de l'institution, domaine.
  3. tofu apply exécute 7 étapes en SSH : prérequis Docker, upload configs et sources, certificats Wazuh, démarrage de la pile, vérification de santé.
  4. Les secrets (PostgreSQL, JWT, Wazuh admin) sont auto-générés et accessibles via tofu output.
  5. Un cron de sauvegarde quotidienne (02h00) est installé automatiquement.
cd deploy/opentofu/ cp terraform.tfvars.example terraform.tfvars nano terraform.tfvars # server_host, institution_name, nexus_domain tofu init && tofu plan && tofu apply tofu output -raw postgres_password

5 Auto-hébergé bare-metal

Pour un RSSI souhaitant contrôler chaque couche. Identique au mode VM, mais sur du matériel physique dédié, sans hyperviseur. Recommandations :

  • RAID 1 ou 10 pour les volumes critiques (TimescaleDB, Wazuh Indexer).
  • Chiffrement LUKS des volumes au repos.
  • Sauvegardes externalisées chiffrées (rsync + GPG ou Restic).
  • Réseau d'administration séparé du réseau d'ingestion des agents.
  • HSM ou Vault pour la clé HMAC maîtresse (rotation périodique).

Fonctionnalités · SIEM & corrélation MITRE

Le pipeline normalise la télémétrie brute vers un schéma ECS-like, extrait les features comportementales d'hôte, puis corrèle pour reconstituer des chaînes d'attaque sur 30 minutes glissantes.

8 techniques MITRE ATT&CK couvertes : T1059 (exécution), T1071 (C2), T1005 (collecte), T1204 (user execution), T1486 (ransomware/impact), T1027 (obfuscation), T1136 (création de compte), T1083 (énumération).

Un incident est levé si ≥ 3 tactiques distinctes sont observées dans la fenêtre, ou si Execution+C2, ou Impact, ou Defense Evasion + Persistence.

Chaque alerte du Modèle 2 est accompagnée du top-3 des features les plus déviantes en écarts-type (σ), avec libellés en clair (« volume de données exportées anormalement élevé : 13.1σ »).

Fonctionnalités · SOAR & garde-fous

Quatre playbooks intégrés : fraude interne, exfiltration, ransomware, anomalie réseau/C2. Chaque action a un niveau d'impact (LOW / MEDIUM / HIGH).

  • Mode Observe (dry_run=True) : aucune action exécutée, tout est journalisé.
  • Mode Semi-auto (défaut prod) : LOW + MEDIUM automatiques si risque ≥ 70 ; HIGH (gel de compte, isolation d'hôte) attend la validation humaine.
  • Mode Auto complet : toutes actions automatisées — non recommandé par défaut.

Fonctionnalités · LLM Analyst bilingue

Chaque incident est expliqué en langage clair (3–5 phrases factuelles) dans la langue choisie : FR ou EN. Deux modes :

  • Template (défaut) : explication déterministe, sans hallucination, sans LLM.
  • LLM (optionnel) : Mistral 7B ou Llama via API compatible OpenAI (Ollama / vLLM, variable OLLAMA_BASE_URL).

Fonctionnalités · Multi-tenant (RLS PostgreSQL)

Une seule instance héberge tous les périmètres. L'isolation est assurée par Row-Level Security PostgreSQL : chaque requête API positionne app.current_tenant avant d'exécuter ses requêtes.

Deux rôles : nexus_app (soumis à la RLS, vue d'un seul périmètre) et nexus_analyst (BYPASSRLS, vue cross-périmètre pour le SOC du CENADI). L'isolation est vérifiée par 8 assertions sur PostgreSQL réel.

Fonctionnalités · Portail PWA

Le frontend (Lot 9) est une Progressive Web App installable. Le service worker met en cache les pages, sert les ressources en mode hors ligne, et reçoit les notifications push pour les alertes critiques.

  • Chrome / Edge : icône « Installer » dans la barre d'adresse.
  • Android : « Ajouter à l'écran d'accueil » — l'app se lance en mode standalone sans barre navigateur.
  • iOS : « Sur l'écran d'accueil » depuis Safari.

Sécurité

  • JWT HS256 maison (auth_middleware), access 15 min + refresh 7 j, auto-refresh sur 401 côté client.
  • Validation HMAC-SHA256 sur chaque lot ingéré, Bearer token vérifié contre le hash en base.
  • Rate limiting : 100 req/min global, 30 req/min sur /ingest (HTTP 429 + Retry-After).
  • Pseudonymisation stable des PII (e-mails, IPs, agent_ids) via HMAC ; mapping pseudonyme → original réservé à l'admin pour enquête légale.
  • CORS configurable via NEXUS_CORS_ORIGINS ; jamais de wildcard avec credentials.
  • Rotation HMAC par agent (POST /provision/rotate-hmac/{agent_id}) et révocation d'urgence par tenant (/provision/revoke-tenant/{tenant_id}).
À durcir en production

Les connecteurs SOAR (gel de compte AD/LDAP, isolation d'hôte, blocage IP périmétrique) sont simulés dans le démonstrateur — à raccorder aux annuaires et pare-feu réels du CENADI avant exploitation.

FAQ

Mon serveur a moins de 8 Go de RAM, est-ce possible ?

Oui. Commentez le service wazuh.dashboard et baissez OPENSEARCH_JAVA_OPTS à -Xms256m -Xmx256m dans docker-compose.yml. Vous gardez l'API REST et le portail mais perdez l'interface SIEM graphique de Wazuh.

Les agents fonctionnent-ils derrière un pare-feu strict ?

Oui — l'agent est egress-only en HTTPS sur le port 443 (configurable). Aucun port entrant requis. Le store-and-forward local conserve les lots si le serveur est momentanément injoignable.

Que se passe-t-il si le serveur tombe quelques heures ?

Les agents continuent à collecter localement. Les lots sont mis en file persistante (taille bornée par queue_max_mb) et rejoués automatiquement à la reprise. Aucune perte d'événements tant que la file n'est pas saturée.

Puis-je remplacer le modèle UEBA par le mien ?

Oui. Tout modèle scikit-learn sauvé en .joblib avec la structure attendue (model, scaler, features, threshold, risk_cfg) est compatible. Déposez-le dans models/model2_isoforest.joblib et redémarrez le scoring service.

Le mode LLM est-il indispensable ?

Non. Le mode template par défaut produit des explications déterministes en français et en anglais, sans risque d'hallucination. Le mode LLM est une amélioration optionnelle pour les explications longues.

Comment intégrer SIGIPES / SYDONIA ?

Dans le mode souverain OpenTofu, l'intégration est faite manuellement par l'équipe SOC du CENADI pendant le raccordement du périmètre. Le Modèle 2 UEBA est calibré sur les patterns d'audit observés. Contactez l'équipe SOC →
